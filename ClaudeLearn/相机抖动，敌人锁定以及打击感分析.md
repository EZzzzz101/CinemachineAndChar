## 第1章 · 虚拟相机思想:Brain 与 VCam,为什么不能直接控制 Camera

### 1.1 一个反直觉的事实

你看到的画面来自 **Main Camera**。但打开场景你会发现,Main Camera 上**几乎没有任何跟随逻辑**——它只挂了一个 `CinemachineBrain` 组件。角色跟随、鼠标转动、拉近拉远这些"意图",全都写在另一个叫 **ThirdPersonCamera** 的物体上(它是一个 `CinemachineVirtualCamera`,简称 **VCam**)。

为什么要把"相机意图"从相机本体上剥出来?答案在下面这 4 个痛点里。

### 1.2 直接操控 `Camera.transform` 的 4 个痛点

假设没有 Cinemachine,你会在自己写的脚本里每帧做:

```csharp
transform.position = player.position + offset;   // 位置
transform.LookAt(player);                        // 朝向
Camera.main.fieldOfView = ...;                   // 镜头参数
```

这样写很快会撞墙:

1. **位置、朝向、镜头参数混在一起**,想要"跟随后再加一个镜头微调"没有插槽;
2. **切相机难**:过场、锁定敌人时要自己写插值,还容易跳变;
3. **多机位难**:同一个画面想从"自由视角"平滑切到"锁定视角",代码量爆炸;
4. **回放/时间缩放难**:回放需要按时间重算相机,手动代码耦合太深。

Cinemachine 的答案一句话:**分工**。把"相机该长什么样"和"相机怎么显示"拆成两层。

### 1.3 分工:Brain(执行者)与 VCam(提议者)

```
┌───────────────────────────────────────────────────────────────┐
│                        Main Camera(真正的相机)                 │
│   Camera 组件 + CinemachineBrain + AudioListener + URP 数据    │
│                                                               │
│   CinemachineBrain 每帧:                                      │
│     1. 找出场景里"最想说话"的那个 VCam(按 Priority 投票)        │
│     2. 把它输出的 CameraState(位置/朝向/镜头参数)混合           │
│     3. 写进 Camera.transform —— 这才是真正动 Camera 的地方     │
└───────────────────────────────────────────────────────────────┘
              ▲ Brain 读(每帧 LateUpdate)
              │
   ┌──────────┴──────────┐
   │   多个 VCam 候选    │  ← 每个都是一个"相机提议"
   │  ThirdPersonCamera  │      Priority = 10
   │  (LockOnCam 运行时)  │      Priority = 20(锁定临时生成)
   │  ...                │
   └─────────────────────┘
```

- **VCam 是一个"相机提议"**:它不直接写 Camera,只是输出一份 `CameraState`(位置、朝向、镜头参数)给 Brain。

- **Brain 是"执行者"**:挂在真正的 Main Camera 上,每帧选一个活跃 VCam,把结果写进 Camera。

> ⚠️ 易错点:VCam 本身也是一个 GameObject,但**它不是"第二台相机"**,只是"第二份候选机位"。场景里真正渲染画面的永远是 Main Camera。

### 1.4 怎么选 VCam:Priority 投票 + Blend 过渡

场景里同时有多个 VCam 时,Brain 按 `Priority` 选**最高分**的胜出。同分则看谁最后被激活。

- `ThirdPersonCamera` 的 Priority = **10**(自由相机);
- 锁定敌人时,`LockOnManager` 会生成一个 Priority = **20** 的索敌相机(见第6章)。

当活跃 VCam 变化时,Brain 会做 **Blend(过渡插值)**:把旧机位平滑混合到新机位,而不是硬切。你项目里默认过渡是 **EaseInOut、2 秒**(Main Camera 的 `m_DefaultBlend`);`LockOnManager` 在运行时会把过渡改成 **0.3 秒**(代码默认 0.25,但场景 Inspector 里 `_blendTime` 序列化成 0.3,以场景为准)——这就是后面锁定相机"平滑甩过去"的原因。

### 1.5 本项目 Main Camera 组件逐个拆

Main Camera 上四个组件,每一个都有用:

| 组件 | 关键值 | 作用 |
|---|---|---|
| `Camera` | FOV 45 · near 0.3 · far 1000 | 真正的渲染相机,镜头参数 |
| `AudioListener` | — | 听到声音的耳朵 |
| **`CinemachineBrain`** | `m_UpdateMethod = LateUpdate` · 默认 blend EaseInOut 2s | 选 VCam、混合、写回 Camera |
| `UniversalAdditionalCameraData` | Base Camera · 后处理关 | URP 给相机挂的数据组件,和 Cinemachine 无关 |

**为什么 Brain 要在 `LateUpdate` 更新?** 因为角色动画、物理结算都在 `Update` 之后才落定。如果 Brain 在 `Update` 里就写相机,相机看到的是一帧"还没移动完"的角色,镜头会抖动。放在 `LateUpdate` 保证"相机永远跟着最终运动后的形态"。(第7章会再见到这个时序。)

### 动手试试

1. 选中 Main Camera,把 `m_DefaultBlend` 的 Time 从 2 改成 0,进 Play 锁定/解锁敌人,感受过渡区别。
2. 把 `m_UpdateMethod` 改成 Update,转视角,感受镜头抖动(看完改回来)。

### 自查题

1. 为什么 Main Camera 上不写跟随逻辑,而要把"跟随意图"放在 VCam 里?
2. 场景里同时有两个 VCam,哪个生效?优先级怎么定的?
3. Brain 为什么用 `LateUpdate` 更新?如果角色位移在 Update 里,用 Update 更新相机会怎样?

<details><summary>答案(先自己答再看)</summary>

1. 因为"相机意图"需要被**复用、组合、切换**:多个 VCam 代表多个机位,靠 Priority 选、靠 Blend 过渡,直接改 Camera 拿不到这套能力。
2. `Priority` 最高的胜出;同分按最后激活顺序。
3. 角色动画/物理在 Update 结算,相机放 LateUpdate 看到的是"结算完"的姿态,不抖。
</details>

## 第2章 · 管线:相机是怎么"算"出来的

### 2.1 概念:VCam 内部的四阶段管线

VCam 拿到 Follow 目标、LookAt 目标、输入之后,内部把"算出最终相机状态"这件事拆成四个**阶段(Stage)**:

```
 Body ──► Aim ──► Noise ──► Finalize
(位置)    (朝向)   (抖动)     (收尾)
```

- **Body(管位置)**:围绕 Follow 目标,决定相机站在哪。
- **Aim(管朝向)**:围绕 LookAt 目标,决定相机朝哪看。
- **Noise(管抖动)**:叠加摄像机噪音(风吹、手持感),本项目没配。
- **Finalize**:收尾阶段,扩展(Extension)在这里做最后修正。

每个阶段由**阶段实现器(Stage Body/Aim/Noise 组件)**执行,它们是**可插拔**的——同一个 VCam,把 Aim 实现器一换,整个机位风格就变了。这是第6章"锁定相机 = 换 Aim 实现器"的底层原因。

> 一句话记忆:**Body 决定"站哪",Aim 决定"看哪"。**

### 2.2 本项目 VCam 的管线配置

打开场景的 `ThirdPersonCamera`(VCam),它的子物体叫 **`cm`**,里面装着实现器:

```
ThirdPersonCamera(VCam, Priority=10)
├─ CinemachineVirtualCamera        ← VCam 本体,存 Lens(FOV45) 和 Follow/LookAt 引用
├─ CinemachineInputProvider        ← 输入源(第3章)
├─ HideCursor / CameraZoom         ← 自定义脚本(第3章)
├─ CinemachineImpulseListener      ← 扩展(第4/5章)
├─ CinemachineCollider             ← 扩展(第4章)
└─ cm(子物体)
   ├─ CinemachinePipeline          ← 内部标记组件(标记"这是管线容器")
   ├─ CinemachineFramingTransposer ★ Body 实现器
   └─ CinemachinePOV               ★ Aim 实现器
```

> 注意:`cm` 子物体上的两个实现器分别是什么——**FramingTransposer 是 Body(管位置),POV 是 Aim(管朝向)**。名字像"Transposer 管转换、POV 管视角",非常容易记反。

### 2.3 FramingTransposer(Body)字段全解

Body 阶段最常用的实现器,本项目里它的设置:

| 字段 | 本项目值 | 含义 |
|---|---|---|
| `m_CameraDistance` | **3** | 相机离目标多远的轨道距离 |
| `XDamping / YDamping / ZDamping` | 0.5 / 0.5 / 0.75 | 跟随的惯性平滑(阻尼) |
| `ScreenX / ScreenY` | 0.5 / 0.5 | 把目标"框"在画面哪个点(0.5=正中央) |
| `m_TargetMovementOnly` | 1 | 相机跟随方式 |
| `GroupFramingMode` | 2 | 对 `CinemachineTargetGroup` 生效(为第6章锁定埋的钩子) |
| `SoftZoneWidth / Height` | 0.8 / 0.8 | 目标在画面中心的软区大小 |

**效果一句话**:FramingTransposer 让"Follow 目标"始终出现在画面中心 `(0.5,0.5)`,并且保持 `m_CameraDistance` 距离。改 `m_CameraDistance` = 拉近拉远(第3章的 CameraZoom 干的就是这个)。

### 2.4 POV(Aim)字段全解

Aim 阶段的实现器,本项目用的是 **POV(Point Of View,第一人称式朝向)**——相机朝哪由鼠标输入直接决定:

| 轴 | 本项目值 | 含义 |
|---|---|---|
| VerticalAxis(俯仰) | 输入 Mouse Y · **Invert=1** · Min -30 / Max 70 · Wrap 0 | 上下看,限位 -30°~+70° |
| HorizontalAxis(水平) | 输入 Mouse X · Min 0 / Max 360 · **Wrap 1** · MaxSpeed 0.22 | 左右环绕,可转满一圈 |
| MaxSpeed / AccelTime / DecelTime | 0.22 / 0.8 / 0.3(水平) | 旋转角速度上限 + 加速/减速平滑 |

**为什么 POV 用在这里?** POV 是"完全由输入旋转"的朝向,不强制看向 LookAt。它把鼠标位移累积成相机朝向角——这正好是第三人称"自由转视角"的手感。(第6章锁定时会换成 **Composer**,那是"盯着目标看"的朝向,两个一对比就懂了。)

### 2.5 易错点:位置和朝向是"耦合"的

新手最容易绕晕的地方:**FramingTransposer 的定位依赖相机的朝向,而朝向由 POV 决定。**

管线里位置和朝向是耦合的:
- 你转鼠标(POV 改朝向)→ 相机朝向变 → FramingTransposer 下一帧按"新朝向"把相机摆在目标后面 `CameraDistance` 处 → 相机绕角色转起来了;
- 你滚轮拉近(FramingTransposer 改距离)→ 只改变远近,不改变朝向。

所以"转视角时相机在绕角色转"不是两套逻辑,而是**一套"朝向驱动位置"**的结果。调参时记住:**Body 的 Damping 是位置平滑,Aim 的 MaxSpeed 是转圈速度上限,两者不是一回事。**

### 动手试试

1. 把 `m_CameraDistance` 从 3 改成 10,进 Play 看目标在画面里变小(拉远)。
2. 把 POV 的 VerticalAxis 的 Max 从 70 改到 45,进 Play 仰头时会被更早限位。

### 自查题

1. POV 和 FramingTransposer,谁管朝向、谁管位置?你怎么从组件名和阶段名推出?
2. 把 `m_CameraDistance` 从 3 调到 10,画面上会发生什么?改的是哪个阶段?
3. 把 POV 的 MaxSpeed 调大,影响的是什么?
4. 为什么说"给 VCam 换一个 Aim 实现器,机位风格就变了"?(为第6章铺垫)

<details><summary>答案</summary>

1. POV 是 Aim 管朝向,FramingTransposer 是 Body 管位置。从名字:Transposer 管"相机怎么摆放"(位置),POV 是"视角"(朝向)。
2. 目标在画面里变小(相机拉远)。改的是 Body 阶段。
3. 转圈(水平旋转)的速度上限,是朝向相关的,不是位置。
4. 因为 Aim 阶段决定"看哪",换了它等于换了一整套视角逻辑,机位风格随之改变。
</details>

## 第3章 · 给管线喂输入:Input System 接入与鼠标操作

### 3.1 谁把鼠标移动喂给 POV?

第2章说了 POV 管朝向,但它需要一个"旋转意图"——**谁来把鼠标位移变成旋转量?**

答案是 `CinemachineInputProvider`。它挂在 VCam 上,`XYAxis` 指向输入资产 `Assets/Input/AnbiInput.inputactions` 里的 **`CameraLook`** 动作(注意:叫 `CameraLook`,**不叫 `Look`**)。这个动作的绑定是:

| 设备 | 绑定路径 |
|---|---|
| 鼠标/触屏 | `<Pointer>/delta`(鼠标每帧位移) |
| 手柄 | `<Gamepad>/rightStick`(右摇杆) |
| 手柄 | `<Joystick>/{Hatswitch}` |

> 关键点:输入不是"每帧手动给 POV 的 axis 赋值",而是让 **Input System 的事件流 → InputProvider → POV 的轴**。POV 的轴把"位移量"累积成"角度",并且带 `MaxSpeed / AccelTime / DecelTime` 平滑,所以鼠标轻轻一动,相机是**平滑转过去**,而不是瞬间跳到新角度。

```
鼠标位移(delta) → Input System → CinemachineInputProvider → POV
                                                             │
                              HorizontalAxis(左右,累加+平滑)  │
                              VerticalAxis(上下,限位-30~70)  ─┘
```

### 3.2 输入资产里都有什么动作、谁在用

`AnbiInput.inputactions`(Player 映射):

| 动作 | 类型 | 绑定 | 谁在用 |
|---|---|---|---|
| `Move` | Value(Vector2) | WASD + 手柄左摇杆 | `MoveInputMY` → 角色移动 |
| `CameraLook` | Value(Vector2) | 鼠标/右摇杆 | `CinemachineInputProvider` → POV |
| `Fire` | Button | 手柄右扳机 | 连招(第8章) |
| `Zoom` | Value(Axis) | `<Mouse>/scroll/y` | **没人用!** 见下 |
| `Dash` | Button | `Shift` | 闪避 |
| `LockOn` | Button | **鼠标中键** | `LockOnManager`(第6章) |

> 💡 细节坑:输入资产里定义了 `Zoom` 动作(滚轮),但 `CameraZoom.cs` **根本没用它**——它是直接读硬件 `Mouse.current.scroll`,绕过了 Input System 资产。这就是为什么你改输入资产的 Zoom 绑定没用,得改代码或让它改走动作。

### 3.3 锁鼠标:HideCursor 与 CameraHideCursor

`Assets/Scripts/Cam/` 下有两个脚本:`HideCursor.cs` 和 `CameraHideCursor.cs`,作用都是隐藏并锁定光标:

```csharp
Cursor.visible = false;
Cursor.lockState = CursorLockMode.Locked;
```

**这两个文件逐字节相同**(坑②,见第9章),留一个即可。它们只改全局鼠标状态,和相机管线没有关系,挂在 Cam 目录纯属巧合。

> 注意:这段逻辑写在 `Start()` 里,**只执行一次**。窗口失焦再回来不会自动重新锁定。

### 3.4 CameraZoom.cs 逐行拆解(滚轮拉近拉远)

```csharp
public class CameraZoom : MonoBehaviour
{
    [SerializeField] private float _minDistance = 1f;   // 最近 1 米
    [SerializeField] private float _maxDistance = 8f;   // 最远 8 米(场景里实际配的是 4)
    [SerializeField] private float _zoomSpeed = 4f;     // 平滑速度
    [SerializeField] private float _sensitivity = 1f;   // 灵敏度(场景里配 0.01)

    private CinemachineVirtualCamera _vCam;
    private CinemachineFramingTransposer _transposer;
    private float _targetDistance;

    void Awake()
    {
        _vCam = GetComponent<CinemachineVirtualCamera>();
        _transposer = _vCam.GetCinemachineComponent<CinemachineFramingTransposer>();
        _targetDistance = _transposer.m_CameraDistance;   // 记住初始距离
    }

    void Update()
    {
        float scroll = Mouse.current.scroll.ReadValue().y;  // 直接读硬件
        if (Mathf.Approximately(scroll, 0f)) return;
        _targetDistance -= scroll * _sensitivity;          // 滚上拉近(负),滚下拉远(正)
        _targetDistance = Mathf.Clamp(_targetDistance, _minDistance, _maxDistance);
    }

    void LateUpdate()
    {
        _transposer.m_CameraDistance = Mathf.Lerp(
            _transposer.m_CameraDistance, _targetDistance, Time.deltaTime * _zoomSpeed);
    }
}
```

逐行要点:
- `Awake` 里用 `GetCinemachineComponent<CinemachineFramingTransposer>()` **取到 Body 阶段实现器**——这是 Cinemachine 暴露阶段实现器的官方 API;
- `Update` 里把滚轮值累加进 `_targetDistance` 并 Clamp 到 `[1, 4]`(场景里配的值);
- **`LateUpdate`** 里用 `Lerp` 平滑逼近——放在 LateUpdate 是为了避开逻辑 Update、跟 Cinemachine 输出时序相容(第7章展开)。

**为什么缩放改距离而不是改 `Camera.fieldOfView`?**
- 改 FOV:透视变形(视野变大/变小),目标在画面里的大小变化不明显;
- 改距离(移动相机):目标和背景一起"推近拉远",第三人称常用。
二者手感完全不同,想要"镜头拉近"就用距离。

### 自查题

1. 鼠标左滑一下,POV 的 HorizontalAxis 值是怎么从 0 长到某个值的?MaxSpeed 起什么作用?
2. 缩放改 `m_CameraDistance` 和改 `Camera.fieldOfView` 有何区别?
3. 为什么说 `CinemachineInputProvider` 只是"搬运工",真正消费旋转的是 POV?

## 第4章 · 扩展机制:Collider 防穿模 + ImpulseListener 震屏

### 4.1 概念:扩展(CinemachineExtension)是什么

Cinemachine 除了 Body/Aim/Noise 三个**阶段实现器**,还有一类组件叫 **扩展(Extension)**。它挂在 VCam 上,可以在管线每个阶段**之后**被回调,不改实现器也能额外修正 `CameraState`。

```
Body → [扩展回调] → Aim → [扩展回调] → Noise → [扩展回调] → Finalize → [扩展回调]
```

本项目 VCam 上有两个扩展,正好是两种典型用途:
- **`CinemachineCollider`**:在阶段间**修正位置**(防穿模);
- **`CinemachineImpulseListener`**:在阶段间**叠加位移**(收震屏)。

### 4.2 防穿模原理:CinemachineCollider

#### 问题从哪来

FramingTransposer 只负责"把相机摆到期望位置",它**不做碰撞检测**。期望位置落在墙里,相机就在墙里——这就是你之前遇到的穿模。

#### Collider 怎么修

Collider 以 **Follow 目标 → 期望相机位置** 的方向打一根**球形射线(SphereCast)**,半径 = `CameraRadius`:

```
       角色(Follow 目标)                     墙
            ●───────────────────────────┃←期望相机位置(在墙里)
            │                          ┃
            └──── SphereCast(带半径) ──┘
                  撞墙 → 相机沿视线拉回到墙前 ●
```

- 用 SphereCast 而不是直线,是因为**镜头有体积**:只挡中心点会剩半个镜头在墙里;
- 撞到**地面**同理:期望位置在地面下方时,球扫先碰到地面,把相机抬到地面之上。

#### 关键:它在哪个阶段执行?

我读了 2.10.7 包源码(`Runtime/Behaviours/CinemachineCollider.cs`):

```csharp
protected override void PostPipelineStageCallback(..., CinemachineCore.Stage stage, ...)
{
    if (stage == CinemachineCore.Stage.Body)   // ← 位置修正在 Body 阶段
    {
        ...
        Vector3 displacement = PreserveLineOfSight(ref state, ref extra);  // 拉回
        ...
        displacement += RespectCameraRadius(cameraPos, lookAt);           // 相机半径修正
        ...
        state.PositionCorrection += displacement;                          // 写回
    }
    if (stage == CinemachineCore.Stage.Aim)    // ← Aim 阶段只做镜头评分
    {
        extra.targetObscured = IsTargetOffscreen(state) || CheckForTargetObstructions(state);
        ... // 只影响 ShotQuality,不影响位置
    }
}
```

**所以:Collider 的"拉回修正"跑在 Body 阶段,Aim 阶段只做遮挡/评分判断。** 网上很多教程说"扩展都在 Finalize",在你这个版本里**不准确**——写代码或排错时要以源码为准。

#### 字段全解(你场景里的值)

| 字段 | 值 | 含义 |
|---|---|---|
| `m_CollideAgainst` | 全部层 | 哪些层算障碍(街道在 Ground 层,包含) |
| `m_IgnoreTag` | **Player** | 忽略这个标签的物体(**关键!**) |
| `m_MinimumDistanceFromTarget` | 0.1 | 相机离目标最近距离 |
| `m_AvoidObstacles` | true | 是否主动避障 |
| `m_CameraRadius` | 0.12 | 球扫半径(镜头粗细) |
| `m_Strategy` | **PullCameraForward** | 沿视线拉回(第三人称标准) |
| `m_MaximumEffort` | 4 | 每帧最多几次球扫(上限,防性能爆) |
| `m_Damping` | 0.2 | 平时跟随平滑 |
| `m_DampingWhenOccluded` | 0.6 | 被挡时推进/退出平滑(防抖) |

**为什么 `m_IgnoreTag = "Player"` 是关键的?** 因为第三人称相机在角色身后,球扫几乎必然先碰到角色的 CharacterController——如果不忽略玩家自己,相机会一直被自己的角色挡住,永远缩到最近距离、镜头怼着后脑勺。

**为什么两个 Damping?** 源码里按位移变化选:被挡的瞬间位移变大(`displacement.sqrMagnitude` 增大)用 `m_DampingWhenOccluded`(0.6,柔和);正常跟随用小一点的 `m_Damping`(0.2,跟得紧)。分开设才不会"咔"一下怼脸。

**`m_Strategy = PullCameraForward`** 的意思:相机沿视线方向(朝目标)被拉回,直到站在障碍物前面。另一种 `PreserveCameraHeight` 是保持高度只水平躲,2D 横版才用。

### 4.3 一键工具:CameraColliderSetup.cs 逐行

这些参数手改很烦,所以做成编辑器工具(`Assets/Editor/CameraColliderSetup.cs`,菜单 **Tools/场景/相机防穿模**):

```csharp
var vcams = Object.FindObjectsByType<CinemachineVirtualCamera>(FindObjectsSortMode.None);
// 找到场景里所有 VCam
foreach (var vcam in vcams)
{
    var collider = vcam.GetComponent<CinemachineCollider>();
    if (collider == null)
    {
        Undo.AddComponent<CinemachineCollider>(vcam.gameObject);   // 挂上扩展
        collider = vcam.GetComponent<CinemachineCollider>();
    }
    ...
    ApplySettings(collider);   // 用源码里确认过的真实字段名(m_CollideAgainst 等)写参数
}
```

要点:
- 扩展必须和 VCam **在同一个 GameObject** 上(它靠 VCam 的扩展列表驱动);
- 用 `Undo.AddComponent` 才能 Ctrl+Z 撤销;
- 字段直接赋 `m_CollideAgainst` / `m_IgnoreTag` / `m_CameraRadius` / `m_Strategy` 等——这些是 2.10.7 的**公开字段**。⚠️ 不同 Cinemachine 版本字段名会变(旧版可能叫 `ObstacleLayerMask`),跨版本写这类工具时先查包源码。

### 4.4 ImpulseListener:震屏的接收端

`CinemachineImpulseListener` 挂在 VCam 上,是**震屏信号的接收端**(第5章讲信号怎么发出来)。它的关键值:

| 字段 | 值 | 含义 |
|---|---|---|
| `m_ChannelMask` | 1 | 只接收通道 1 的信号 |
| `m_Gain` | 1 | 增益(整体放大/缩小震动) |
| `m_ApplyAfter` | **2** | 在哪个阶段之后叠加 |
| `m_UseCameraSpace` | 1 | 按相机空间叠加位移 |

`m_ApplyAfter = 2` 对照 `Stage` 枚举(`Body=0, Aim=1, Noise=2, Finalize=3`)= **Noise 之后**。也就是说:**震屏是在相机的最终位置算完之后,叠加一层临时位移**——它不参与 POV 的朝向计算,所以震屏不会"带跑"你的视角(第7章再展开)。

### 自查题

1. 为什么 Collider 要 `m_IgnoreTag="Player"`?如果不忽略,会发生什么?
2. `m_ApplyAfter=2` 在 Stage 枚举里是哪个阶段?震屏发生在什么时候叠加?
3. 把 `m_CameraRadius` 调大,效果是更"贴近墙"还是更"远离墙"?`m_MaximumEffort` 太小会怎样?
4. `m_Damping` 和 `m_DampingWhenOccluded` 分别在什么时刻生效?

<details><summary>答案</summary>

1. 第三人称相机在角色身后,球扫会先碰到角色自己的碰撞体,不忽略的话相机永远拉不开。忽略 Player 标签即可。
2. `2 = Noise`,震屏在相机最终状态算完后叠加一层临时位移。
3. 调大 CameraRadius = 镜头变粗,离墙更远(更保守);MaximumEffort 太小 = 每帧只扫几次,复杂地形可能拉不干净。
4. 位移变化大(被挡)用 DampingWhenOccluded,正常跟随用 Damping。
</details>

## 第5章 · 相机抖动:Impulse 信号链与 CameraShake 拆解

### 5.1 概念:Impulse 是"信号广播/订阅"链

震屏在 Cinemachine 里走的是 **Impulse(冲击)** 机制,本质是**广播/订阅**:

```
某处 GenerateImpulseWithForce(力)
   → ImpulseSource(信号源)按"通道(Channel)"广播一条冲击信号
   → 任何 ImpulseListener 只要 ChannelMask 覆盖该通道,就接收
   → 把信号叠加到相机最终状态上(第4章讲过:m_ApplyAfter=2=Noise之后)
```

本项目的两端:

| 端 | 谁 | 关键配置 |
|---|---|---|
| 信号源 | 场景里叫 **CameraShake** 的空物体上的 `CinemachineImpulseSource` | Channel=1 · Shape=Explosion(3) · 包络 Attack0/Sustain0.2/Decay0.7 |
| 接收端 | `ThirdPersonCamera` 上的 `CinemachineImpulseListener` | ChannelMask=1 · Gain=1 |

**为什么震动用 Impulse,而不是每帧直接改 `Camera.transform.position += Random.insideUnitSphere`?**

1. **自动衰减**:信号带时间包络(attack→sustain→decay),不需要你手动收;
2. **不污染相机意图**:抖动是叠加在最终状态上的临时扰动,不参与 POV/位置计算,不会"带跑"视角;
3. **多相机自动同步**:所有挂了匹配 Listener 的相机同时震;
4. **可配合时间缩放**:有 `IgnoreTimeScale` 开关(第8章顿帧的关键)。

### 5.2 信号源的配置长什么样

打开场景的 `CameraShake` 物体,`CinemachineImpulseSource` 的关键序列化值:

| 字段 | 值 | 含义 |
|---|---|---|
| `m_ImpulseChannel` | 1 | 发到通道 1 |
| `m_ImpulseShape` | 3 | 波形种类:0=Custom 1=Recoil 2=Bump **3=Explosion** 4=Rumble(爆炸型,方向随机爆散) |
| `m_ImpulseDuration` | 0.2 | 信号总时长 |
| `m_TimeEnvelope.AttackTime` | 0 | 起振时间(瞬间起) |
| `m_TimeEnvelope.SustainTime` | 0.2 | 保持时间(保持峰值 0.2s) |
| `m_TimeEnvelope.DecayTime` | 0.7 | 衰减时间(0.7s 内衰减到 0) |
| `m_AmplitudeGain` / `m_FrequencyGain` | 1 / 1 | 幅度/频率增益 |
| `m_DefaultVelocity` | (-0.25, 0.3, 0.2) | 默认震动方向 |
| `m_ImpactRadius` | 100 | 影响半径(远处也收得到) |

时间包络示意(这就是"卡一下然后自己消掉"的来源):

```
振幅
1 │    ▄▄▄▄▄▄▄▄
  │   ████████████
  │  █             █
  │ █               ██
  │█                  ████
  └──────────────────────────→ 时间
    Attack=0  Sustain=0.2   Decay=0.7
```

### 5.3 CameraShake.cs 逐行拆解

`Assets/Scripts/Manager/CameraShake.cs` 是对 ImpulseSource 的**轻量封装**:

```csharp
public class CameraShake : Singleton<CameraShake>
{
    private CinemachineImpulseSource _impulseSource;

    protected override void Awake()
    {
        base.Awake();
        _impulseSource = GetComponent<CinemachineImpulseSource>();       // 找信号源
        if (_impulseSource == null)
            _impulseSource = gameObject.AddComponent<CinemachineImpulseSource>();

        if (CinemachineImpulseManager.Instance != null)
            CinemachineImpulseManager.Instance.IgnoreTimeScale = true;   // ← 全局开关!
    }

    public void TriggerShake(float force)
    {
        _impulseSource?.GenerateImpulseWithForce(force);
    }
}
```

要点:
- 信号源组件在哪?在**挂着 CameraShake 脚本的同一个物体**上(Awake 里 get-or-add);
- `GenerateImpulseWithForce(force)`:**力越大振幅越大**,direction 用 `m_DefaultVelocity` 的方向;
- ⚠️ **`CinemachineImpulseManager.Instance.IgnoreTimeScale = true` 是"全局"设置**,设在整个 Impulse 管理器上,不是单个 Source 上。它的作用是:即便 `Time.timeScale ≈ 0`(顿帧),震屏仍按真实时间走完。这就是第8章顿帧时"画面定住但镜头还在震"的那把钥匙。

### 5.4 唯一触发点:连招命中

震屏不是每帧都响,而是**连招命中时触发一次**。在 `ATKingState.ATK()`(动画关键帧调用的攻击事件):

```csharp
public void ATK()
{
    var step = ResuableData.CurrentStep;
    int idx = ResuableData.currentATKIndex;

    // 震屏
    if (step.shakeForceList != null && idx < step.shakeForceList.Length)
    {
        float force = step.shakeForceList[idx];
        if (force > 0f) CameraShake.Instance.TriggerShake(force);
    }
    // 顿帧(第8章)
    if (step.hitPauseList != null && idx < step.hitPauseList.Length)
    {
        float duration = step.hitPauseList[idx];
        if (duration > 0f) HitPauseManager.Instance.Trigger(duration, step.hitPauseScale);
    }
    ResuableData.currentATKIndex++;   // 同一段多次命中,每次取不同下标
}
```

数据来自 `ComboStepData` 的 `shakeForceList`(每段多次命中,每次一个力度)。当前 `AnBiComboConfig.asset` 里配的是:

| 段 | 动画 | shakeForceList | hitPauseList |
|---|---|---|---|
| 1 | Anbi_Normal_1 | (空) | (空) |
| 2 | Anbi_Normal_2 | `[0.15]` | (空) |
| 3 | Anbi_Normal_3 | (空) | (空) |
| 4 | Anbi_Normal_4 | `[0, 0, 0.3]`(第3击才震,力度 0.3) | (空) |
| 5 | Anbi_Normal_5 | `[0, 0.2]`(第2击震 0.2) | (空) |

> ⚠️ **顿帧已接线但数据全空**:`hitPauseList` 目前每段都是 `[]`,也就是说 `ATK()` 里的顿帧分支永远不会触发。想让连招有"卡肉感",往 `hitPauseList` 里填非 0 秒数即可(第8章)。

### 5.5 易错点

1. **`force` 不是"随机大小"**:它是包络的**缩放系数**。波形本身(Explosion)自带随机方向,force 只决定振幅;
2. **IgnoreTimeScale 是全局设置**:改的是 `CinemachineImpulseManager.Instance`,不是某个 Source 的 Inspector 开关;
3. **改动力的手感**:想整体更猛 → 调大 Listener 的 `Gain` 或调大 force;想让震动"更长" → 调大 Source 的 `Sustain/Decay`。

### 动手试试

1. 在任意脚本里调 `CameraShake.Instance.TriggerShake(1f)`,感受基准强度;
2. 把 Listener 的 `Gain` 从 1 改到 2,同样 force 更震;
3. 把 Source 的 DecayTime 从 0.7 改到 1.5,震动"拖尾"变长。

### 自查题

1. 为什么震动不用"每帧 `Camera.transform.position += Random.insideUnitSphere`"?至少说出两点。
2. `force` 影响的是波形的什么?它是不是"随机大小"?
3. 把 Listener 的 ChannelMask 改成 2,而 Source 是通道 1,会发生什么?
4. `IgnoreTimeScale` 是在哪个对象/管理器上设置的?它和顿帧有什么关系?(预告第8章)

<details><summary>答案</summary>

1. ① 没有自动衰减,要自己收;② 直接改 transform 会把"相机意图"和"抖动"搅在一起,平滑/碰撞/混合全乱;③ 多相机没法自动同步。
2. force 缩放包络振幅,方向由波形(Explosion)决定,不是随机大小。
3. 通道对不上,Listener 收不到信号,不震(要 ChannelMask 与 Source 的 Channel 匹配)。
4. 设在全局的 `CinemachineImpulseManager.Instance` 上;顿帧时 timeScale≈0,设了它震屏才不被"冻住"。
</details>

## 第6章 · 敌人锁定:双 VCam + Priority 切换 + 角色转向

### 6.1 锁定系统的三层数据源

先分清三个脚本各管什么:

| 脚本 | 职责 | 关键点 |
|---|---|---|
| `Targetable.cs` | "我是可被锁定的生物"标记 | `OnEnable` 自动注册到 TargetManager,`OnDisable` 注销;有 `Team` 枚举(Player/Enemy/Neutral) |
| `TargetManager.cs` | 登记表 + 查询 | 维护 `AllTargets` 列表;提供 `FindNearest` 等 |
| `LockOnTarget.cs` | 提供"锁定位移点" | `lockOnPointOffset`(场景里敌人配了 y=2) |

```
Targetable(标记生物) ──OnEnable──► TargetManager(登记表)
                                        │ AllTargets
LockOnManager.FindNearestTarget ◄───────┘  ← 从这里挑敌人
```

### 6.2 目标搜索:距离 + 视角夹角 + 评分

`LockOnManager.FindNearestTarget()` 逐敌人:

```csharp
Vector3 toTarget = target.GetLockOnPosition() - cam.position;
float dist = toTarget.magnitude;
if (dist > _lockRange) continue;                    // 太远(>15m)不要

float angle = Vector3.Angle(cam.forward, toTarget.normalized);
if (angle > _lockViewAngle) continue;               // 偏离视角中心(>60°)不要

float score = dist + angle * 0.5f;                  // 综合评分:距离 + 夹角
if (score < bestScore) { bestScore = score; best = target; }
```

- 只锁 `Team.Enemy`、且必须挂 `LockOnTarget`;
- 评分 = `距离 + 夹角×0.5`,取最小——"近且正对屏幕"的目标优先;
- 脱锁只按距离(>20m 就解锁,不管朝向,方便你背对敌人跑)。

### 6.3 核心思想:双 VCam,而不是两台相机

锁定/解锁的"平滑镜头过渡"来自**两个 VCam 抢 Priority**:

```
同一台 Main Camera(一个 Brain)
├─ freeCam  = ThirdPersonCamera(POV,Aim=自由转视角)     Priority 10
└─ lockOnCam= 运行时克隆的 LockOnCam(Composer,Aim=咬目标) Priority 20(锁定时)
```

- Brain 只认**活跃 VCam**(Priority 最高那个),从 10 切换到 20 会触发 **Blend** 过渡(0.3s,见场景 `_blendTime`);
- 你看到的"相机平滑甩向敌人"就是这段 Blend,不用自己写插值。

**为什么不直接"关闭 Main Camera、打开另一台相机"?**
- 那样拿不到混接(没有 Blend),要自己写插值,还会闪;
- 双 VCam 方案里渲染的还是同一台 Main Camera,只是"候选机位"换了,天然无缝。

### 6.4 为什么要"克隆"而不是手写新 VCam

```csharp
_lockOnCam = Instantiate(_freeCam, _freeCam.transform.parent);   // 克隆
_lockOnCam.name = "LockOnCam";

var inputProvider = _lockOnCam.GetComponent<CinemachineInputProvider>();
if (inputProvider != null) Destroy(inputProvider);               // 去掉输入

_lockOnCam.DestroyCinemachineComponent<CinemachinePOV>();        // 换 Aim
_lockOnCam.AddCinemachineComponent<CinemachineComposer>();

_lockOnCam.LookAt = _targetGroup.transform;                       // 看向"玩家+敌人"的组
_lockOnCam.Priority = 0;                                          // 先藏起来
```

克隆的好处:**自动继承 Body(FramingTransposer)、Lens(FOV45)等设置**,只把 Aim 从 POV 换成 Composer。这样锁定后"距离、FOV 跟自由相机完全一致",只是朝向逻辑变了。第4章给 Collider 也是这个 clone——锁敌相机也防穿模、也震屏(第7章会提到)。

### 6.5 Composer vs POV:为什么锁定要用 Composer

| | POV(自由) | Composer(锁定) |
|---|---|---|
| 朝向由谁定 | 鼠标输入直接转 | 盯着 LookAt 目标,把目标维持在画面软区里 |
| 玩家能转视角吗 | 能 | 不能(镜头咬住目标) |
| 适合 | 自由探索、转视角 | 锁定战斗、过场跟随 |

所以锁定后你转鼠标**不会**甩开镜头——Composer 会持续把"目标组(玩家+敌人连线的中点)"框在画面里。

### 6.6 先对齐再切 Priority:为什么过渡不跳变

`Lock()` 里这两行是关键:

```csharp
_lockOnCam.transform.position = _freeCam.transform.position;   // 先让索敌相机"等于"自由相机当前姿态
_lockOnCam.transform.rotation = _freeCam.transform.rotation;
_lockOnCam.Priority = 20;   // 再提优先级 → Blend 从同一点出发
_freeCam.Priority   = 10;
```

如果不先对齐,两个 VCam 的起点不同,Blend 会从很远的地方"飞"过去。解锁(`Unlock()`)反过来:**先把 freeCam 瞬移到 lockOnCam 的姿态,再降 Priority**——于是 0.3s 的滑回是从"锁定视角"平滑回到"自由视角"。

### 6.7 角色转向:HandleRotation / FaceEnemy / FlashToEnemy

`PlayerController` 里两套转向:

```csharp
// 平时:跟随相机方向 + 摇杆(见第7章数据流)
public void HandleRotation()
{
    Vector2 input = MoveInput.MoveValue;
    if (input.magnitude < 0.1f) return;
    Vector3 moveDir = CameraManager.Instance.GetMoveDir(input);   // 相机 forward/right 合成
    transform.rotation = Quaternion.Slerp(transform.rotation, Quaternion.LookRotation(moveDir), Time.deltaTime * rotationSpeed);
}

// 锁定态:直接面向敌人(覆盖上面的逻辑)
public void FaceEnemy()
{
    if (!LockOnManager.HasInstance || !LockOnManager.Instance.IsLockedOn) return;
    Vector3 dir = LockOnManager.Instance.CurrentTarget.GetLockOnPosition() - transform.position;
    dir.y = 0;
    transform.rotation = Quaternion.LookRotation(dir);
}
```

还有 `FlashToEnemy()`:够近(<3m)就瞬间闪到敌人正前方 1.5m 处,用于近战起手。

### 6.8 LockOnUI:指示器

`LockOnUI.cs` 每帧把锁定目标的世界坐标转屏幕坐标,画一个 UI 指示器;当目标在相机后方(`screenPos.z < 0`)时隐藏——防止"指示器反着指向屏幕外"。

## 第7章 · 一帧完整数据流:从输入到画面

这一章把前六章拧成一条线。我们追踪"按一次鼠标 + 按一次中键"时,同一个 VCam 与 Main Camera 在一帧里发生了什么。

### 7.1 帧内执行顺序

Unity 主循环里,**每个脚本的 Update 都先跑完,然后所有 LateUpdate 才跑**,再渲染。这个顺序决定了"相机 vs 角色"谁先:

| 阶段 | 谁在动 | 干什么 |
|---|---|---|
| `Update` | Input System(默认 Dynamic) | 处理鼠标/摇杆事件 |
| | `MoveInputMY` | 读 `MoveValue` |
| | `LockOnManager` | 监听中键、找目标、切 Priority |
| | 角色 `PlayerController.Update` | `LocomotionState.Update()` → `HandleRotation()` 转向 |
| | `CameraZoom.Update` | 读滚轮,累加 `_targetDistance` |
| | POV 轴 | 把输入累积成朝向角 |
| `LateUpdate` | **`CinemachineBrain`** | 选活跃 VCam → 跑管线 → 写回 `Camera.transform` |
| | `CameraZoom.LateUpdate` | `Lerp` 把 `m_CameraDistance` 逼近 `_targetDistance` |
| 渲染 | GPU | 按 Camera 最终状态画一帧 |

**关键结论:角色在 Update 里转向,用的是上一帧 LateUpdate 定好的相机朝向。** 因为相机永远"慢半拍"算出最终朝向,角色就跟着这个"已成事实"的方向走——所以不会出现"角色和相机互相追"的抖动。

### 7.2 全链路(按下鼠标/中键的一帧)

```
① 鼠标移动 / 中键
   │
   ├──► Input System 事件
   │        ├─► CinemachineInputProvider → POV 轴(朝向角)      [第3章]
   │        └─► LockOnManager.OnLockOnInput → ToggleLockOn      [第6章]
   │
② VCam 管线(被 Brain 调用,LateUpdate 内)
   │    1. POV(Aim)     按输入产出"相机朝向"                    [第2章]
   │    2. FramingTransposer(Body) 按朝向+Follow 目标产出期望位置 [第2章]
   │    3. CinemachineCollider(扩展) Body 阶段 SphereCast,被挡拉回 [第4章]
   │    4. CinemachineImpulseListener(扩展) Noise 之后叠加震屏    [第4/5章]
   ▼
③ Brain 拿最终 CameraState →(若刚切换 VCam,做 Blend 过渡)→ 写 Camera.transform
   │
   ▼
④ 角色(Update)
      MoveValue ──► CameraManager.GetMoveDir(读相机 forward/right 去 y)
                      ──► HandleRotation: Slerp 转向相机相对方向   [第6章]
      (锁定态:FaceEnemy 直接面向敌人,覆盖第④步)
```

### 7.3 震屏为什么不会"带跑"视角

震屏(第5章)是 ImpulseListener 在 **Noise 之后**叠加的**临时位移**,它改的是最终 `CameraState` 的位置,不参与 POV 的朝向计算。所以:

- 震屏时画面在抖,但鼠标转视角的**参照系**没变;
- 你震完一松手,相机回到"该有的位置",不会因为刚才抖过而偏掉。

### 7.4 锁定 + 震屏同时发生

锁定时活跃 VCam 是 `LockOnCam`,而它是**克隆**自 freeCam 的——第4章的 Collider 也是被一键工具批量挂到所有 VCam 上的。所以:

- 锁定相机**同样防穿模**(继承 Collider);
- 锁定相机**同样震屏**(继承 ImpulseListener);
- 这就是为什么"锁定打敌人时,镜头咬住目标、命中震屏、且不会穿墙"三件事同时成立。

<details><summary>答案</summary>

## 第8章 · 打击感:震屏 + 顿帧联动与数据流

### 8.1 打击感都有哪些要素

一套有手感的近战连招一般由这些构成(本文只深拆后两样):

```
命中判定 → 受击动画 → 伤害数字 → 音效 → 特效(VFX) → 震屏 → 顿帧(卡肉感)
```

前四样大多在 `CharacterAudio` / `CharacterVFX` / 受击逻辑里,本文重点拆 **震屏** 和 **顿帧**,以及它们怎么**联动**。

### 8.2 数据入口:ComboStepData

`Assets/Scripts/Character/Core/Combo/ComboStepData.cs` 里定义了每段连招的打击感数据:

```csharp
[Header("震屏")]
public float[] shakeForceList;   // 每段多击力度(0=不震)
public float[] hitPauseList;     // 顿帧时长(0=不卡)
[Range(0f, 1f)] public float hitPauseScale = 0.05f;   // 顿帧时间缩放倍率
```

为什么是**数组**?因为一段攻击可能命中多次(比如第4段打 3 下),`ATK()` 每次用 `currentATKIndex` 取**不同下标**的力/顿帧值——所以可以做到"第1击轻、第3击重"。

### 8.3 ATK():两条并行支线

`ATKingState.ATK()`(动画关键帧事件调用)是唯一触发点:

```
动画关键帧 → PlayerController.ATK() → Action.ComboState.ATK()
                                        │
                    ┌───────────────────┴───────────────────┐
                    │ shakeForceList[idx] > 0               │ hitPauseList[idx] > 0
                    ▼                                       ▼
        CameraShake.TriggerShake(force)        HitPauseManager.Trigger(duration, scale)
        → ImpulseSource → Listener → 相机抖     → Time.timeScale≈0.05 → 几乎冻结
                                               → unscaled 计时器 0.x s 后恢复
```

两条支线**同时出发**:画面几乎定格(顿帧)的同时,镜头还在震(因为 IgnoreTimeScale 豁免了震屏)。

### 8.4 顿帧怎么实现:HitPauseManager + GameTimer

`HitPauseManager.cs` 只有 3 行核心:

```csharp
public void Trigger(float duration, float timeScale = 0.05f)
{
    Time.timeScale = timeScale;                                    // 全局冻结到 0.05
    TimerManager.Instance.GetRealTimer(duration, () => Time.timeScale = 1f);  // 到点恢复
}
```

`GameTimer` 的计时用的是 **`Time.unscaledDeltaTime`**(不受 timeScale 影响):

```csharp
public void Tick()
{
    if (!_running) return;
    _remaining -= Time.unscaledDeltaTime;   // 真实时间,不是缩放时间
    if (_remaining <= 0f) { _callback?.Invoke(); _running = false; }
}
```

所以整个流程是:

```
Time.timeScale = 0.05   ← 动画/粒子几乎全冻住(卡肉感)
    │
    └─ GameTimer 用 unscaledDeltaTime 照常倒数
        │
        └─ 到点 → Time.timeScale = 1f(恢复正常)
```

### 8.5 联动的钥匙:IgnoreTimeScale

还记得第5章 `CameraShake.Awake` 里那句:

```csharp
CinemachineImpulseManager.Instance.IgnoreTimeScale = true;
```

顿帧时 `Time.timeScale ≈ 0.05`,如果**没设**这句,Impulse 按缩放时间衰减,会把震动一起"冻住"——画面定格了镜头也不震,卡肉感就没了。设了它,震动按**真实时间**走完,于是:

> **画面几乎定格,但镜头还在震** —— 这就是"卡一下 + 抖一下"的组合拳手感。

### 8.6 易错点

1. **顿帧是"全局"的**:`Time.timeScale` 影响所有依赖 scaledDeltaTime 的东西(动画、粒子、相机 zoom 的 Lerp)。这是双刃剑,所以震屏特意用 IgnoreTimeScale 豁免。
2. **`GetRealTimer` 不是"不暂停"**:它只是在暂停期间用 unscaledDeltaTime 继续倒数。两者要分清。
3. **顿帧期间输入还会被读到**:连招靠 `canATK` / `hasBufferedInput` 等窗口锁控制,防止顿帧期间误触发下一段。
4. 当前 `hitPauseList` 全空 → 顿帧分支永远不会走。**想体验卡肉感,先去 `AnBiComboConfig.asset` 填数据**。

### 动手试试

1. 打开 `Assets/SO/AnBiComboConfig.asset`,把某段 `hitPauseList` 填 `0.1`,进 Play 打那一击,感受顿帧;
2. 把 `hitPauseScale` 改 0.1,感受"冻得更死"的效果;
3. 临时注释掉 `IgnoreTimeScale = true` 那行,再打一次,对比"顿帧时震动被冻住"的手感差异。

2. `GameTimer` 用什么时间计时?这跟"timeScale 冻结"为什么能共存?
3. 把 `hitPauseList` 填入一段 0.1s 的数据,预期画面会发生什么?会不会把动画一起冻住?

<details><summary>答案</summary>

1. `CinemachineImpulseManager.Instance.IgnoreTimeScale = true`(CameraShake.Awake 里设的全局开关)。
2. `Time.unscaledDeltaTime`。它不经过 timeScale 缩放,所以 timeScale 冻结时它照常走。
3. 命中瞬间 timeScale≈0.05,动画/粒子几乎定格约 0.1s(按真实时间),同时镜头震;0.1s 后恢复。动画确实会被一起冻住,这就是卡肉感。
4. 因为一段攻击可能命中多次,每次按 currentATKIndex 取不同的力/时长,支持"第1击轻、第3击重"。
</details>

## 第9章 · 常见坑与排查清单

### 坑①:VCam 的 Follow/LookAt 可能是悬空引用(最重要)

场景里 `ThirdPersonCamera` 的 Follow/LookAt 指向 `安比.prefab` 内部的一个 Transform(fileID `165128694801375592`)。我在 `Assets/Prefabs/安比.prefab` 里**搜不到**这个 fileID——也就是说这个引用很可能**断了**(预制定位丢失)。

**症状**:相机不跟随角色、或跟随的是个空引用。

**排查**:Unity 里打开场景 → 选中 `ThirdPersonCamera` → 看 Inspector 里 Follow/LookAt 是否显示 **Missing(红框)**。

**修复**:若是,把 `安比` 角色身上的一个 Transform(建议新建一个空物体放头顶当"跟随点")拖进 Follow/LookAt 即可。

> 注意:锁定用的 TargetGroup 在运行时由 LockOnManager 生成/管理,但它也依赖 `_playerTransform`(用 tag=Player 找),所以这个问题会影响自由相机跟随。

### 坑②:HideCursor 和 CameraHideCursor 是重复文件

`Assets/Scripts/Cam/` 下两个脚本**逐字节相同**,都是锁鼠标。留一个即可,别改其中一个忘另一个(行为对不上)。

### 坑③:MoveInput.cs 是遗留代码,且类名大小写有坑

- `MoveInput.cs` 是旧实现(自己算速度/转向/位移),现在角色实际用 **`MoveInputMy.cs`**;
- ⚠️ **类名是 `MoveInputMY`(大写 Y),文件名是 `MoveInputMy.cs`**——写代码/搜索时注意大小写不一致,容易踩坑。

### 坑④:顿帧已接线但数据全空

`AnBiComboConfig.asset` 里 `shakeForceList` 有值(0.15/0.3/0.2),`hitPauseList` 每段都是 `[]`。**顿帧逻辑是好的,只是没配数据**——想有卡肉感就去填。

### 现象 → 可能原因排查表

| 现象 | 可能原因 | 排查/修法 |
|---|---|---|
| 相机完全不跟随,像钉死 | 坑① Follow/LookAt 悬空 | Inspector 看是否 Missing,重拖引用 |
| 镜头穿墙 | Collider 没挂 / `m_IgnoreTag` 配错 | Tools/场景/相机防穿模;确认 IgnoreTag=Player |
| 穿模但只穿某几个物体 | 那个物体没有碰撞体 | 检查模型是否开了 Generate Colliders / 手动加碰撞体 |
| 震屏没反应 | Source 的 Channel 和 Listener 的 ChannelMask 对不上 | 两边通道要匹配 |
| 顿帧瞬间震动被冻住 | 没设 `IgnoreTimeScale` | CameraShake.Awake 里确认那行还在 |
| 锁定后视角还能被鼠标转 | lockOnCam 没换上 Composer,或 Priority 没切 | 看 LockOnManager 日志/Inspector |
| 锁定过渡从很远飞过来 | 切换前没对齐两个 VCam 姿态 | 检查 Lock()/Unlock() 里的对齐代码 |

### 调试三板斧

1. **Cinemachine 调试视图**:选中 Main Camera,Inspector 里打开 Cinemachine Brain 的 Debug 面板,能实时看活跃 VCam、Blend 进度;
2. **日志**:`LockOnManager.Update` 每 60 帧会打当前活跃相机和是否在 Blend;`Targetable.OnEnable` / `LockOnUI` 也都有日志;
3. **二分**:把震屏 force 调成常量 1、把 blendTime 调 0,快速隔离"参数问题"还是"逻辑问题"。

### 排查决策树

```
相机不跟随? ──► 查 Follow/LookAt 引用(坑①)→ 是否 Missing
镜头穿墙?  ──► 查 Collider 是否挂了、IgnoreTag 对不对
不震屏?    ──► 查 Channel / ChannelMask 是否匹配
顿帧冻住震动? ─► 查 IgnoreTimeScale 是否在
锁定转不动视角? ─► 查 lockOnCam 的 Aim 是不是 Composer、Priority 是不是 20
```

### 自查题

1. 相机完全不动、像被钉死,最可能先查哪两处?
2. 为什么"直接改 Camera.transform 做震屏"会和三块知识(管线/锁定/顿帧)打架?
3. 如果震屏效果在顿帧瞬间"卡住不动",应该改哪个开关?
4. 项目里为什么有两份几乎一样的锁鼠标脚本?如何安全地只留一份?

<details><summary>答案</summary>

1. ① Follow/LookAt 引用是否 Missing;② VCam 是否 active 且 Priority 最高。
2. 直接改 transform 会绕开管线(丢混合/碰撞/延迟)、绕开锁定(丢 Composer 咬合)、绕开顿帧(IgnoreTimeScale 只对 Impulse 生效)。
3. 补上 `CinemachineImpulseManager.Instance.IgnoreTimeScale = true`。
4. 历史遗留(一个是旧写法一个是新写法忘了删)。安全做法:确认两文件逐字节相同后,删其中一个,并把它的 .meta 一并删除,重新编译确认无引用。
</details>

**进阶:自己写一个 CinemachineExtension**

```csharp
using Cinemachine;
using UnityEngine;

/// <summary>示例:每个阶段之后把相机抬高一点</summary>
public class LiftCameraExtension : CinemachineExtension
{
    [SerializeField] private float _lift = 0.1f;

    protected override void PostPipelineStageCallback(
        CinemachineVirtualCameraBase vcam,
        CinemachineCore.Stage stage, ref CameraState state, float deltaTime)
    {
        if (stage == CinemachineCore.Stage.Finalize)
            state.PositionCorrection += Vector3.up * _lift;
    }
}
```

挂在 VCam 上即可,它会在每帧管线结束后修正位置——这就是 Collider/ImpulseListener 背后同一套机制。

## 附录C · 调参速查卡

| 想达到什么手感 | 改哪个参数 | 调法 |
|---|---|---|
| 镜头转得太慢/太快 | POV 的 `MaxSpeed`(水平/垂直) | ↑转快 ↓转慢 |
| 镜头太"颠"(跟随抖) | FramingTransposer 的 `Damping` | ↑更稳 ↓更跟手 |
| 拉近拉远范围 | CameraZoom 的 `_minDistance/_maxDistance` | 按需 |
| 穿模还是穿 | Collider 的 `m_CameraRadius` | ↓贴墙更紧(可能穿)↑更保守 |
| 贴墙太"弹" | Collider 的 `m_DampingWhenOccluded` | ↑更柔 |
| 震屏太猛/太弱 | ImpulseListener 的 `Gain` 或 force 值 | ↓减震 ↑加震 |
| 震动拖尾太长/太短 | ImpulseSource 的 `DecayTime` | ↓短促 ↑拉长 |
| 顿帧太久/太短 | ComboStepData 的 `hitPauseList` | ↓减秒 ↑加秒 |
| 顿帧冻得不够死 | ComboStepData 的 `hitPauseScale` | ↓更死(→0) ↑更活 |
| 锁定过渡太跳/太慢 | LockOnManager 的 `_blendTime` | ↑更慢更顺 ↓更快更脆 |
| 锁定的目标搜索范围 | LockOnManager 的 `_lockRange/_lockViewAngle` | 按需 |
| 锁定后镜头咬得太死 | Composer 的 `SoftZoneWidth/Height` | ↑更松(目标更晚跟) |
